1 · What it does

unity-cli is a Claude skill. With it, Claude works on a Unity project the same way you would: through the Editor that is already open in front of you, over the official Unity CLI.

That covers scenes, GameObjects, components, transforms, prefabs, materials, shaders, lighting, animation, Timeline, assets, UPM packages, project settings, play mode, console errors, screenshots, tests and builds.

It does not create projects, install Editors, or handle licensing. That stays in Unity Hub.

1.1 · Why it exists

Anything an agent does by hand-editing Unity's YAML is a guess. Going through the running Editor means the change is made by Unity itself: serialization stays valid, prefab links survive, and a wrong answer shows up as a console error rather than a corrupted scene.

The other half of the idea is the shared macro library. When Claude works out a compact command that any Unity project could reuse — a search, a digest, an audit — it becomes a macro, and one library is shared by every project on your machine. The library gets sharper the more projects it is used against.

1.2 · Requirements

  • Unity 6.0 or newer. The CLI bridge does not exist on older versions, and the skill stops rather than falling back to hand-editing YAML.
  • Windows only, for now. See below.
  • Claude Desktop or Cowork, and Git.

2 · Read before installing

Four things about this skill that aren't obvious, and that you should agree to before it runs.

Windows only

The macro library path is hardcoded to C:/unity-cli-skill throughout the skill. It will not work on macOS or Linux as-is.

It creates C:/unity-cli-skill

A Claude skill lives in a temporary, session-scoped folder that is deleted afterwards. So on first run the skill clones the repo to C:/unity-cli-skill and uses that as the permanent home for the shared macro library. That clone, not the installed skill copy, is the source of truth from then on.

It edits Packages/manifest.json

Once per project, on the first run. Two dependencies get added: com.unity.pipeline (the CLI bridge itself) and com.unitycli.macros, linked as a local package from file:C:/unity-cli-skill/macros.

That means every Unity project on this machine shares a single macro library — which is the point, and also the constraint. Claude tells you before it writes to the manifest.

It asks two setup questions

On first run, once per machine. Both are explained in section 6.

3 · Prerequisites

3.1 · The Unity CLI

Installed and signed in. In PowerShell:

$env:UNITY_CLI_CHANNEL='beta'; irm https://public-cdn.cloud.unity3d.com/hub/prod/cli/install.ps1 | iex

Reopen your terminal, then:

unity --version
unity auth login

The CLI is Unity's own tool and is currently on the beta channel. Unity's install docs are the authoritative source if that command changes.

3.2 · The Unity Pipeline package

Needed in the project you want to work on. Open the project in Unity, then from the project directory:

unity pipeline install
unity pipeline list

Pipeline: Installed means you're set. Requires Unity 6.0+. The skill can do this step for you and will ask first, since it modifies your project. See the Unity Pipeline package docs.

3.3 · Git

For the C:/unity-cli-skill clone and macro updates.

4 · Install

  1. If you might contribute a macro back, fork the repo first, using Fork at the top right of the GitHub page. Contributions go through your fork, and having it up front saves a detour later. Skip this if you just want to use the skill.
  2. Download it. Code ▸ Download ZIP on GitHub, from your fork or from the main repo — the contents are the same.
  3. Install the ZIP as a skill. In Claude Desktop or Cowork, open Settings, find the Skills section, and upload the ZIP.
  4. Restart Claude, then ask for something Unity-shaped. The skill triggers on its own.
Open the repo ↗

5 · First run

The first run costs some extra tokens, because of the setup process. Open your project in Claude Code or the code section of Claude Desktop, and ask Claude to do something. With the Editor open on your project, Claude will:

  1. Clone the repo to C:/unity-cli-skill.
  2. Ask you the two setup questions, and save your preferences to C:/unity-cli-skill/settings.local.json.
  3. Check the project is on Unity 6.0+ and wired up with the Unity CLI, adding the two packages if needed.
  4. Ask you to click on the Unity Editor window, because a manifest change is only picked up when the Editor regains focus. Then it waits out the package resolve and domain reload, which can take a couple of minutes.
  5. Get on with what you actually asked for.
Once only

Steps 1 to 4 are first-run only. Later sessions start at step 5.

6 · The two questions

Answers are stored in C:/unity-cli-skill/settings.local.json, which is per-machine, gitignored, and never committed. Delete that file to be asked again.

QuestionYesNo
Auto-update
the macros?		 Before each run, fetches the shared repo and rebases C:/unity-cli-skill on top of it, so you pick up macros other people have contributed while keeping your own. It never discards your local work: if the rebase can't complete, Claude aborts it, says so, and carries on. The library stays exactly as you left it. Update it yourself with git pull --rebase upstream main whenever you feel like it.
Contribute
macros?		 When Claude writes or improves a macro while working, it commits it, pushes a branch to your fork, and opens a pull request — asking you first, every time. Nothing is ever pushed to the shared repo. Macros are written to C:/unity-cli-skill/macros and left uncommitted, local to your machine.

Claude decides whether something is a macro while it works: a one-off query runs through eval and is thrown away, while a shape that any project could reuse becomes a macro. Most sessions produce none, and that's the expected outcome.

7 · What's inside

PathWhat it is
SKILL.md The instructions Claude follows: setup, the seven steps, the contribution flow.
macros/ The shared m_* macro library, a Unity UPM package (com.unitycli.macros) that gets linked into each project. Compact, token-cheap commands for searching, digesting and auditing a project.
references/talk-to-editor.md The operating manual: addressing objects, which macros to prefer, eval rules, how to write a macro.
references/eval-cookbook.md Working C# snippets for running through eval.
references/troubleshooting.md Bridge not responding, compile errors, stale handles, exit codes.
Project-agnostic by design

Macros carry no hardcoded scene names, layer conventions, or a game's own types, and no hard dependency on optional packages. A macro that only pays off in one project makes the shared set worse for everyone.

8 · Contributing

It's open source, and the whole point is that it gets better with contributors. The macro library is only as good as the number of Unity projects it has been sharpened against.

The shared repo takes pull requests only; nobody pushes to it directly. With contribute: yes, Claude does the mechanical part: it commits the macro, pushes it to a macro/<name> branch on your fork (it asks for the fork URL once and remembers it), and — after checking with you — opens the PR with gh. If gh isn't set up, it hands you the link instead.

Your local C:/unity-cli-skill stays on main throughout. Claude never checks out a branch there, because that directory is a live Unity package: switching away would delete the macro off disk and out of every project on your machine. One branch per contribution, but they only exist on your fork, so nothing piles up locally. GitHub doesn't auto-delete fork branches — merged or closed, they stay until someone removes them, and they're harmless if you don't.

8.1 · Good contributions to make

  • A macro that answers a kind of question any Unity project could ask.
  • An improvement to an existing macro, such as a missing filter or a better output shape. This beats adding a new one, because it costs the shared set nothing in surface area.
  • A line in references/ that would have saved you a failed first attempt.
